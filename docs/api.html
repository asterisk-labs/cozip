API

Python, R and Julia share libcozip; JavaScript reads archives with fetch. This page covers their common rules. Each language page has types and examples.

How it works

A cozip is an ordinary ZIP with a small index at byte 0 that points to a Parquet manifest. The manifest lists each file's byte range and can carry your metadata. The figures below compare its size and read path with an ordinary ZIP.

The figures use one reference archive, measured on a laptop: a million files of 1,000 bytes, 000000.tif to 999999.tif, with six columns of metadata. The code examples further down use cities.zip, a small public archive on Hugging Face and Source Cooperative, so you can run them. Step through each figure with the names under it or the arrow keys.

An ordinary ZIP keeps its table of contents, the Central Directory, at the end, so finding one file takes three requests one after another. The directory has a 46-byte record plus the name for every file, 56 MB for the reference archive, and no columns to choose files by.

A cozip reader never parses the Central Directory, which stays valid for ZIP tools. The index also holds a profile byte. These packages write and read Flat archives, whose only indexed file is the manifest, and the TACO package writes and reads TACO archives. The specification defines every byte.

What the reader fetches instead of the directory is the manifest, a Parquet table.

Listing the plain ZIP of the same million files with Python's zipfile takes 1.6 s and gives names and sizes only. cozip.read returns the whole manifest, with a location for every file, in 0.32 s. All timings are on a laptop, from local disk.

Python, R and Julia read through one C reader, in four steps.

  1. Both ends, at once. It asks for the first 64 KiB and the last 32 KiB together. The head holds the __cozip__ header and the index, and the tail holds the ZIP end records.
  2. Checks. Before it trusts an offset, it checks the header, the index and the profile in the order of section 8.5, recomputes the integrity hash, and requires the end record to be the last 22 bytes. A failure stops the read with the code section 9 gives it.
  3. The manifest. If the manifest lies in either range, the reader already has it, as with any archive up to 64 KiB. Otherwise one more request fetches it with its local header, which must match the index.
  4. Your files. The manifest is now a table in memory, so filtering it costs no request. Each file you open is one range request, or one for a run of neighbouring files.
archiverequests before the first file
The manifest lies in the first 64 KiB or the last 32 KiB2, sent at once

If the server sends a strong ETag, the later requests carry it in If-Match, so an archive replaced between two requests fails the read. Without one, the check of the manifest's local header can still catch a replaced archive, but not every replacement of the same size.

The JavaScript reader makes the same checks. It sends its ranges one at a time and skips the ones the first response already covers, so a small archive takes one request. Its page lists them.

Write

The writer takes a table with one row per file. name is the file's name in the archive, path is where it is on disk, and every other column goes into the manifest, in its order.

Files are stored in table order. Sort the table first, by split, tile or date, so that files read together sit next to each other and can come back in one request.

Before it writes a byte, the writer refuses:

  • a table with no rows, or without name and path;
  • a column named offset, size, cozip:location or taco:location in any letter case, since the writer and the reader compute them;
  • two columns whose names differ only in case, which DuckDB cannot tell apart when it reads the manifest;
  • a name that breaks the name rules, or one of the reserved names __cozip__, __metadata__ and __cozip_padding__;
  • a missing or empty file, and an output that is also one of the sources.

The archive is written under a temporary name, checked against the plan, hashed, then renamed over the output, so a failed write leaves an existing file untouched. A source whose size changes during the write is an error. The C page lists every check.

In two stages

write writes a compressed manifest with the Parquet writer of each language. To choose your own writer or options, such as GeoPandas for a GeoParquet manifest or a set row group size, split the call in two.

  1. stage_metadata plans the archive without writing anything. It returns the manifest table, with name, then offset and size as uint64, then your columns, and the (name, path) pairs in the same order. path is dropped, and the schema metadata of the input is kept, so a GeoParquet geo key survives.
  2. Write that table as a Parquet file with any library.
  3. stage_create writes the archive with that file stored byte for byte as __metadata__. It never rewrites it, so its compression, row groups and key-value metadata stay as you wrote them.

The Parquet must keep name as a string and offset and size as uint64 (spec 13.3), and must not hold path, a location column or two names that differ only in case. With validation on, the default, stage_create plans the paths again and stops at the first row whose name, offset or size differs. Turning it off skips only that comparison: a wrong manifest then makes a valid ZIP whose rows point at the wrong bytes.

Keep the pairs in the manifest's row order. If you sort or filter the table between the two calls, apply the same order to the pairs, or plan again. Each call reads the sizes from disk, so with validation on, a file that changed in between shows up as a mismatch.

Read

read returns the Flat manifest with one row per file: name, offset, size, your columns and cozip:location. Native reads take two or three requests; JavaScript takes one to three. Other profiles fail with PROFILE in the native bindings and UNKNOWN_PROFILE in JavaScript. Read TACO archives with the TACO package.

sourceAn ASCII path or URL in the native bindings; an ASCII HTTP(S) URL in JavaScript.
columnsThe extra columns to return. name, offset and size always come back. Names are matched with case, and one the manifest does not have is an error. cozip:location, taco:location and cozip:gdal_vsi in the list are ignored. Left out, every column comes back.
locationFalse leaves out cozip:location.

Python, R and Julia decode the manifest with DuckDB. Extension autoloading and autoinstall are off, so DuckDB downloads and loads nothing, and Hive partitioning is off, so a key=value folder in the path adds no column. A stored cozip:location, taco:location or cozip:gdal_vsi column, which no conforming writer produces, is dropped in any case and the location is computed again. A manifest with two columns that differ only in case is refused.

Sources

cozip:location joins the byte range of a row with the source of the archive.

Python, R, Julia and C read through Karu, which takes these sources. The archive part of the location repeats the source as given, wrapped for GDAL.

A relative path stays relative, so read with an absolute path or a URL when the locations will be used from another directory or machine. The JavaScript reader takes http:// and https:// URLs only.

Verify

verify checks the access path of any profile, TACO included, without decoding its manifest. It accepts unknown profile values, as spec 7.1 allows. Native bindings accept the sources below; JavaScript accepts HTTP(S). It returns nothing when its checks pass and names the first rule that fails.

It uses the first 64 KiB, the last 32 KiB and any missing index bytes. JavaScript reuses the first response when it holds the whole archive. The check does not parse the Central Directory, compare indexed names with ZIP entries, enforce profile rules or check payloads. A changed payload outside the hash window can pass.

cozip.verify("https://huggingface.co/datasets/asterisk-labs/cozip-api-fixtures/resolve/v0.1.0/data/cities.zip")   # None

Open a file

A row's file is the size bytes that start at offset, stored as they were. GDAL opens it through cozip:location, so rasterio, terra, GeoPandas and other GDAL-based readers need no extraction:

ogrinfo -ro -so -al "/vsisubfile/1092_172,/vsicurl/https://huggingface.co/datasets/asterisk-labs/cozip-api-fixtures/resolve/v0.1.0/data/cities.zip"

Any client that reads a byte range reads it too. HTTP ranges include their last byte, so the range is offset to offset + size - 1, and this returns the 172 bytes of cities/paris.geojson:

curl -L -r 1092-1263 https://huggingface.co/datasets/asterisk-labs/cozip-api-fixtures/resolve/v0.1.0/data/cities.zip

Files next to each other come back in one request. Fetch from the first offset to the end of the last file and slice. The bytes between two files are a local header, 30 bytes plus the name, and 20 more for a ZIP64 entry.

GeoParquet manifests

A manifest with a geometry column and the geo key is a GeoParquet file (spec 13.6). Readers that know GeoParquet, such as DuckDB, GeoPandas and the playground map, can pick files by location before fetching any. The others see an ordinary manifest.

Without crs in the geo key, the coordinates are longitude and latitude, OGC:CRS84. Python, R and Julia return the geometry as WKB without the CRS, and JavaScript returns a GeoJSON geometry. Each language page shows how to write one.

Hosting

Upload the .zip to a bucket, Hugging Face or Source Cooperative. Publish a new version at a new key or revision, because readers may hold offsets from the old one, and pin revisions in tests and training runs. For a collection that changes in parts, use several archives. Their manifests concatenate, because each cozip:location names its archive.

The server must answer range requests with the stored bytes.

requirementwhy
Answer Range with 206 and a valid Content-Range: bytes start-end/total.Readers fetch a few small ranges. The JavaScript reader takes the archive size from Content-Range and checks every response against the range it asked for, accepting an end clamped to the last byte.
Apply no Content-Encoding on the fly.Offsets, sizes and the hash refer to the stored bytes.
Keep the object unchanged during a read.A 412, a new ETag or a new size between two responses fails the read.
For browsers, allow the Range header across origins and expose Content-Range with Access-Control-Expose-Headers.Otherwise the browser hides the header and the read fails with range response has no valid Content-Range header.
For browsers, allow If-Match when ETag is exposed.The reader sends a strong ETag back as If-Match, and the preflight would refuse it.

Hugging Face and Source Cooperative do this for public files. An S3, GCS or Azure bucket serves ranges as stored, unless the object was uploaded with a Content-Encoding, and needs a CORS rule only for browsers. To check an upload, run verify on its URL, or paste a public URL into the playground.

SQL with DuckDB

The optional cozip_reader extension reads manifests in SQL and queries a Parquet file stored inside an archive in place. It lives in its own repository with its own versions, and nothing in these packages installs or loads it. Its README lists its functions.

INSTALL cozip FROM community;
LOAD cozip;

SELECT name, offset, size
FROM read_flat('https://huggingface.co/datasets/asterisk-labs/cozip-api-fixtures/resolve/v0.1.0/data/cities.zip')
WHERE continent = 'Europe';
