cozip03 / 8

An ordinary ZIP lists its files at the end

A reader starts at the end of the archive. The last 98 bytes say where the directory starts.

Then it reads the whole directory, one record per file with its name, size and offset. For a million files that is 56 MB.

Only then does it know where the file is. Three reads in a row before the first byte of data.

Measured on a million files of 1,000 bytes. That many entries need the ZIP64 end records, 98 bytes in all.

cozip04 / 8

cozip reads the manifest, not the directory

The reader asks for the first 64 KiB. At byte 51 the index says where the manifest is.

Then it reads the manifest, one row per file with its offset, size and your columns. Here that is 11.7 MB with six metadata columns, a fifth of the directory.

The row gives the exact bytes, so the next read is the file. The Central Directory is never parsed.

The same million files. The manifest holds name, offset, size and six metadata columns in 11.7 MB of Parquet.

Every manifest has name, offset and size. Any other column is yours: here a split, a date, cloud cover and a land cover class.

Query it like any table. cloud_cover < 25 keeps three of these rows, and on all million rows DuckDB filters split, cloud cover, date and area in 35 ms.

With all six columns the manifest is a fifth of the directory: 11.7 MB against 56 MB. With only name, offset and size it is 0.5 MB.

The reference archive: a million files of 1,000 bytes. Its manifest also has lon and lat. Timings on a laptop, from local disk.

Any ZIP tool lists it. cozip adds an index and a manifest.

__cozip__
the index, always the first entry
__metadata__
the manifest, 11.7 MB of Parquet here
__cozip_padding__
only in an archive under 32,819 bytes, so not in this one; readers ignore it

Direct ranges work because files keep their bytes.

Stored, never compressed
a file is its original bytes, at an offset with a size
No encryption, no data descriptors
nothing to decode between the offsets
One segment, no comment
the end record is always the last 22 bytes
Unique ASCII names
with / as the separator and no folder entries
ZIP64 when needed
above 4 GiB, or from 65,535 entries
